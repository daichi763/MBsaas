## 1. 背景・現状システム概要

Field OS は通信人材会社(携帯ショップ・家電量販店・催事・光回線等への人材派遣/請負)向けの運営標準化SaaS。

- **技術スタック**: Hono (TypeScript) + Cloudflare Pages/Workers + Cloudflare D1 (SQLite) + Cloudflare R2 (写真保存)。フロントエンドは Vanilla JS SPA (hash routing) + TailwindCSS CDN。
- **現状のマルチテナント設計**: 全テーブルが `company_id` に紐づき、企業ごとに閉じたデータ構造。
- **現状の人物管理**: `users`(ログインアカウント) 1:1 `staff_profiles`(スタッフ詳細)。いずれも単一企業専属で、他社との連携概念が存在しない。

現状のDBスキーマ全体は `migrations/0001_initial_schema.sql` 以下の各マイグレーションファイルを参照すること。既存テーブル: `companies`, `users`, `sessions`, `staff_profiles`, `clients`, `report_templates`, `projects`, `shifts`, `attendance_reports`, `daily_reports`, `evaluations`, `follow_logs`, `notices`, `notice_reads`, `consultations`。

### 参考にしたkintoneアプリ構造(調査済み)

ユーザーが現在運用しているkintoneアプリ2つを調査し、今回の設計のベースとした。

1. **社員名簿**(全118フィールド): 雇用形態・契約情報・給与体系(月給/日給/時給/役員報酬)・各種手当・銀行口座・社会保険番号・雇用保険番号・マイナンバー・緊急連絡先など、**雇用元企業のみが保持すべき機微な雇用管理情報**。
2. **人材マスタ**(全47フィールド+サブテーブル2種): 氏名・フリガナ・性別・年齢・顔写真・所属区分(プロパー/外注/その他)・所属会社・所属先担当者・稼働状況・経験スキル・職務経歴(サブテーブル)・人材タグ・スキルシート・**コメント(サブテーブル: 表示可否・コメント本文・記載日・担当者)**。こちらは**稼働先企業と共有する前提の情報**。

→ 「社員名簿」=従業員管理、「人材マスタ」=スタッフマスタ、という対応関係が今回の要件の原型になっている。人材マスタの「所属:その他(スキルシート作成のみ)」という選択肢が、後述する「スキルシートのみ作成」ルートの元ネタ。

## 2. 絶対に譲れない要件(変更不可)

以下はユーザーとの合意事項であり、実装方針を変えても必ず満たすこと。

1. **企業間で共有されるのは「スタッフマスタ」相当の情報のみ**。「従業員管理」(雇用形態・給与・社保・口座・マイナンバー等のセンシティブ情報)は雇用元企業以外に一切公開しない。
2. **システム全体でユニークな人物ID**を持ち、QRコードまたはIDによって企業間でスタッフ情報を連携できる。
3. **QRコードは恒久的に固定**(再発行・有効期限の概念は不要)。
4. **他社スタッフをスタッフマスタに連携登録する際は、毎回、同意確認ポップアップを表示**する(共有される情報範囲を明示)。同意履歴は記録として残すこと。
5. **編集権限**: スタッフマスタは**所属元企業のみが全項目編集可能**。稼働先企業は**追記(評価・稼働メモ等)のみ**可能で、氏名・スキル等の基本項目は編集不可(閲覧のみ)。
6. **必須項目のカスタマイズ**: 「絶対必須」の基本識別情報(氏名・性別等)を除き、各項目を必須/任意にするかは**利用企業ごとに設定可能**にする。
7. **ログインは統合**: 同一人物が複数企業に所属していても、**ログインアカウントは1つ**で、企業を切り替えて操作できる。
8. **勤怠報告は企業切替が不要**: スタッフが打刻した情報は、その日のシフト情報に基づいて**自動的に該当する企業・案件に振り分けられる**。
9. **企業間チャット機能**: スタッフマスタ画面に、**所属元企業の担当者 と 稼働先企業の担当者** がやり取りできるチャット欄(右下ウィジェット等)を設ける。
   - 新着メッセージがあれば管理画面ダッシュボードに通知を表示する。
   - 会話履歴はすべて保存し、後から閲覧できる。
   - **スタッフ本人はこのチャットを一切閲覧・参加できない**。スタッフ向け画面(マイページ等)には絶対に表示しないこと。UI上にも「このやり取りはスタッフ本人には表示されません」という趣旨の注記を、チャット欄の近くに明記すること。
10. **スタッフマスタは4つのルートすべてで新規作成可能**にする(詳細は第4章):
    - ①QRコード/IDから自動作成(他社の既存スタッフを連携)
    - ②従業員管理(社員名簿)から作成(自社雇用者)
    - ③取引先から作成(所属会社がField OSを利用していない場合)
    - ④スキルシートのみ作成(稼働管理を行わず、スキルシート発行のみが目的)

## 3. データモデル設計方針

以下は現時点での設計案。第0章の方針に従い、より良い設計があれば代替可。

```
persons (人物マスタ: システム全体で1人1レコード、企業に非依存)
   ├── employments (従業員管理 = 旧kintone「社員名簿」相当。雇用元企業のみアクセス可)
   └── staff_rosters (スタッフマスタ = 旧kintone「人材マスタ」相当。企業間で共有)
         ├── roster_field_requirements (企業ごとの項目必須/任意設定)
         ├── roster_comments (所属元⇔稼働先 担当者間チャット。スタッフ本人には非公開)
         ├── roster_consents (連携時の同意履歴)
         └── shifts / attendance_reports / daily_reports / evaluations / follow_logs / consultations (既存テーブル。staff_id経由でstaff_rostersに接続)

partner_organizations (取引先マスタ: Field OS未契約の所属元企業を登録するための軽量マスタ)
```

### 3.1 `persons`(新規)
システム全体でユニークな人物そのもの。企業に属さない。
- `person_id`: システム全体で一意な主キー(UUID等)
- `global_staff_code`: QRコード化する、人が読める一意コード(恒久固定、失効・再発行の概念なし)
- 氏名・フリガナ・性別・生年月日など、企業を跨いでも変わらない基本情報

### 3.2 `employments`(新規 = 従業員管理)
雇用元企業のみが読み書き可能。他社からは一切参照不可(APIレベルで遮断)。
- `person_id` + `company_id` の組で一意
- kintone「社員名簿」の主要フィールドを踏襲: 雇用形態、契約形態、契約期間、入社日/退職日、在籍状況、役職、勤務形態、給与体系(月給制/日給制/時給制/役員報酬)、基本給、各種手当、総支給額、控除、銀行口座情報、社会保険番号、雇用保険番号、マイナンバー、緊急連絡先、有給・扶養情報 等

### 3.3 `staff_rosters`(既存 `staff_profiles` を発展的に置換 = スタッフマスタ)
企業間で共有される情報のみを保持。既存の `staff_id` を極力継承し、シフト・勤怠・日報等の外部キー関係を壊さないようにする。
- `staff_roster_id`(= 旧 `staff_id` を継承)
- `company_id`: このレコードを保有する企業(=稼働先として見えている企業)
- `person_id`: 紐づく人物
- `owner_company_id`: **所属元企業**(全項目編集権限を持つ企業。NULL可 = 取引先/スキルシートのみの場合など、Field OS上に対応する企業が存在しないケース)
- `affiliation_type`: 作成ルートの区分。`own_employee`(自社雇用) / `linked_external`(他社からのQR連携) / `partner_manual`(取引先から手動登録) / `skillsheet_only`(スキルシートのみ)
- kintone「人材マスタ」の主要フィールドを踏襲: 氏名・フリガナ・性別・年齢・顔写真、所属区分、稼働開始可能日、ステータス(稼働中/募集中/終了)、通勤可能時間、最寄駅、経験・スキル(自由記述)、職務経歴(複数件)、人材タグ、スキルシート(ファイル)
- 項目を「所属元管理項目(氏名・スキル等、所属元のみ編集可)」と「稼働先追記項目(現場評価・稼働メモ等、稼働先も編集可)」に分類できる設計にすること

### 3.4 `partner_organizations`(新規 = 取引先マスタ)
Field OSを利用していない所属元企業を記録する軽量マスタ。表記ゆれ防止のため、都度自由入力ではなく登録済みリストからの選択を基本とし、必要なら新規登録もできるようにする。
- `partner_org_id`, `company_id`(登録した側の企業), `partner_name`, 連絡先等

### 3.5 `roster_field_requirements`(新規 = 必須項目カスタマイズ)
- `company_id` × 項目コード × `is_required` の組。「絶対必須」項目(氏名・性別等)は対象外でシステム固定とする。

### 3.6 `roster_comments`(新規 = 担当者間チャット)
- `staff_roster_id`, 送信元企業, 送信者ユーザー, 本文, 送信日時
- **重要: このテーブルへのアクセスは管理系ロール(company_admin / field_manager / sales_manager / office_staff 等)のみに限定し、`role = staff` は完全に除外すること。** スタッフ向けAPI・画面には絶対に露出させない。
- 未読管理を持たせ、ダッシュボード通知に接続する

### 3.7 `roster_consents`(新規 = 連携同意履歴)
- QR/ID連携で他社スタッフを自社のスタッフマスタに追加する際、毎回の同意確認結果を記録(誰が・いつ・どの連携に対して同意したか)

### 3.8 既存テーブルへの影響
- `users` に `person_id` を追加し、ログインアカウントと人物マスタを紐づける(統合ログインの実現)
- `staff_id` を参照している既存テーブル(`shifts`, `attendance_reports`, `daily_reports`, `evaluations`, `follow_logs`, `consultations`)は、`staff_rosters.staff_roster_id` への参照として維持し、既存データ・既存ロジックへの影響を最小化する

### 3.9 データ移行
- 既存 `staff_profiles` の1レコード → `persons` 1件 + `staff_rosters` 1件(`affiliation_type='own_employee'`, `owner_company_id`=自社)に変換
- `staff_id` の値を変えずに移行し、既存の外部キー関係を維持する

## 4. スタッフマスタ 新規作成の4ルート

「+新規追加」時に、以下4つの作成方法を選択できるUIにする。

| ルート | 想定ケース | 所属元の実体 | 編集権限 |
|---|---|---|---|
| ①QRコード/IDから自動作成 | 他社(Field OS利用企業)に既に登録済みのスタッフを、稼働先が連携登録する | 他社(Field OS利用企業) | 所属元企業が全項目編集可/稼働先は追記のみ |
| ②従業員管理(社員名簿)から作成 | 自社が雇用している従業員をスタッフマスタにも登録する | 自社 | 自社が全項目編集可 |
| ③取引先から作成 | 所属会社がField OSを利用していない場合。取引先マスタから選択(または新規登録)し手動入力 | 取引先(Field OS未契約) | 登録した企業が全項目編集可(事実上の唯一の管理者) |
| ④スキルシートのみ作成 | 稼働管理(シフト・勤怠・日報)を行わず、スキルシート発行のみが目的の最小登録 | 未確定 | 登録した企業が全項目編集可 |

- ①のフローでは、連携登録の直前に**必ず同意確認ポップアップ**を表示し、共有される情報範囲(スタッフマスタ項目のみ)を明示すること。同意結果は `roster_consents` に記録。
- ④のフローでは、スキルシート出力に必要な最小限の項目(氏名・経験・スキル・職務経歴・顔写真等)のみを必須とし、既存の「スキルシート自動生成(印刷対応)」機能をそのまま活用できるようにする。
- いずれのルートでも、「絶対必須」項目以外は企業ごとの必須設定(3.5)が適用される。

## 5. 企業間チャット機能の詳細要件

- 設置場所: スタッフマスタの詳細画面(右下のチャットウィジェット等、UI設計は実装者の裁量でよい)
- 参加者: **所属元企業の担当者** と **稼働先企業の担当者**(管理系ロールのみ)
- **スタッフ本人は閲覧・参加ともに不可**。スタッフ向け画面(`/staff` 配下)には一切露出させないこと。
- チャット欄の近くに「このやり取りはスタッフ本人には表示されません」という趣旨の注記を明記すること。
- 返信があった場合、管理画面のダッシュボードに通知(未読バッジ等)を表示する。
- 会話履歴はすべて保存し、後から遡って閲覧できるようにする。

## 6. 権限制御まとめ

| 項目分類 | 所属元企業 | 稼働先企業 | スタッフ本人 |
|---|---|---|---|
| スタッフマスタ基本項目(氏名・スキル等) | 編集可 | 閲覧のみ | 閲覧のみ(自分の情報) |
| スタッフマスタ追記項目(現場評価・稼働メモ) | 閲覧可 | 編集可 | 不可 |
| 従業員管理(給与・社保等) | 編集可(自社分のみ) | 不可(参照不可) | 不可 |
| 担当者間チャット | 閲覧・投稿可 | 閲覧・投稿可 | **不可(完全非表示)** |
| 勤怠・シフト情報 | 閲覧可(自社が絡む分) | 閲覧可(自社が絡む分) | 自分の分のみ閲覧・入力可 |

## 8. 実装にあたっての注意事項

- 本プロジェクトは Cloudflare Pages / Workers 上で稼働する。D1(SQLite)・R2の制約(Node.js API不可、fsモジュール不可等)を踏まえて設計すること。
- 既存の認証方式(SHA-256ハッシュ + httpOnly Cookieセッション)、マルチテナント構造(`company_id`ベース)との整合性を保つこと。
- 既存機能(シフト管理・勤怠報告・日報・評価・実績分析・請求前チェック等)を壊さないよう、既存の `staff_id` 参照は可能な限り維持する形で移行すること。
- マイグレーションファイルは `migrations/` 配下に連番で追加し、既存の `0001`〜`0004` を変更しないこと。
- 本番環境: Cloudflare Pagesプロジェクト名 `mbsaas`、D1データベース `mbsaas-production`、R2バケット `mbsaas-attendance-photos`。デプロイ済みで本番URLは https://mbsaas.pages.dev/ 。GitHubリポジトリ `daichi763/MBsaas`(mainブランチ)と連携済み。本番D1には現時点でテストデータは未投入(テーブルスキーマのみ)。

3. 大きな設計変更を伴う場合は、着手前にユーザーとフェーズ分け・優先順位を確認する。
