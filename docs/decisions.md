## 応募・認証・個人情報

### D-01 応募のロボット判定ができなかったときは受け付けて「要確認」にする（#501 B）
- **決定**: 公開の募集ページで、Cloudflare Turnstile への問い合わせ（siteverify）が失敗した・タイムアウトした（5秒）ときは、応募を拒否せずに受け付け、`recruit_applications.turnstile_unverified = 1` の印を付ける。管理画面の応募一覧に「要確認」の印を出し、絞り込める。判定に落ちた（`success = false`）応募は今までどおり受け付けない。IP ごと・電話番号ごとの回数の制限は印の有無にかかわらず効かせる。
- **理由**: Cloudflare 側の障害で応募が止まると、募集の機会を失う。いたずらは回数の制限と、管理者の承認（承認しないとシフトにならない）で止められる。
- **根拠のコード**: `src/recruit.ts:280`（判定）、`src/recruit.ts:304`〜`311`、`src/recruit.ts:650`〜`651`（一覧の絞り込み）、`migrations/0087_followups_b.sql:17`

### D-02 パスワード再設定の画面に Turnstile は付けない（#382 A。変更なし）
- **決定**: 再設定のメールを送る画面には、IP ごとの回数の制限（`login_attempts` の `scope = 'reset_ip'`）だけを置き、Turnstile は付けない。応答の文言は、アカウントの有無によらず同じ。
- **理由**: 回数の制限で足りると判断した。さらに本番は今メールを送っていない（D-31）。
- **根拠のコード**: `src/api.ts:600`、`src/api.ts:608`〜`613`

### D-03 他社との共有範囲は A 案（同意の版 v3）（#9001）
- **決定**: 企業間のスタッフ連携で、連携先に見せるのは次の範囲だけにする。
  - 共有する: 氏名・フリガナ・性別・**年代**（生年月日から計算。生年月日そのものは渡さない）・所属会社名と所属先担当者名・最寄駅・通勤可能時間・稼働開始可能日・稼働可能エリア・スキル・経歴・PR ポイント。
  - 共有しない: 従業員管理の情報（雇用形態・給与・手当・口座・住所・社会保険と雇用保険の番号・緊急連絡先など）、連絡先（電話・メール）、生年月日、**備考**（所属元だけの項目）、履歴書などのファイル、所属元の社内メモ・評価・フォロー履歴。
  - 連携先は、所属元の行の基本項目を**その場で読む**（写しを持たない）。連携先は基本項目を編集できない（403）。
  - 同意の文面の版は v3。同意した版と範囲は `roster_consents` に残る。v2 からは共有を減らす変更なので、既存の連携の同意の取り直しはしない。
- **理由**: 他社に渡す個人情報を、仕事の割り当てに要るものだけにするため。
- **根拠のコード**: `src/roster.ts:218`〜`233`（`CONSENT_VERSION`・`SHARED_SCOPE`・`NOT_SHARED_SCOPE`・`ROSTER_OWNER_ONLY_FIELDS`）、`src/lib/tenant.ts:39`〜`46`（他社に返すメールアドレスを伏せる）。詳細は [spec_multi_company_staff.md](spec_multi_company_staff.md) の 6.1。

### D-04 連携先の電話番号は照合にだけ使い、所属元から照合のときに読む（#123 C）
- **決定**: 所属元で電話番号を変えたとき、連携先の行に番号を写さない。連携先で「同じ人か」を電話番号で照らす（応募と既存のスタッフの照合など）ときは、所属元（雇用元）の行の今の番号をその場で読む。照合の結果にも番号は入れない。所属元が連携を終えた行は、所属元の番号を見ない。
- **理由**: 連絡先は共有しない（D-03）。写すと連携先の DB に番号が残る。一方で、古い番号で照合して別の人と取り違えるのも防ぎたい。
- **経緯**: 2026-10-20 の判断では「連携先の行の番号も更新し、照合にだけ使う」としていたが、実装では写さずに照合のときに読む形（C）にした。
- **変更（Sprint 24 #9969 authz-08。総点検の修正計画）**: 番号が一致するかを確かめるだけでも、手元の番号がその人のものかを連携先が知れてしまう（共有しない項目を照合に使っている）ため、他社連携の行の電話番号は照合に使わないことにした。他社連携の行は、氏名などの共有する項目で照合する。上の「決定」のうち、所属元の番号を読む部分はもう使わない。
- **根拠のコード**: `src/staff-lifecycle.ts:101`〜`105`（`MATCH_PHONE_SQL`・`withSharedPhone`）、`src/staff-lifecycle.ts:83`（`findStaffByPhone`）

### D-05 予備コードの作り直しはパスワードの確認だけ・TOTP の秘密鍵は暗号化しない（#544 A。変更なし）

### D-15 「取引先」を「協力会社」に改名し、クライアントとつなぐ（B 案）
- **決定**:
  - 画面の「取引先」を「協力会社」に改名する。データと API のパスは変えない（`staff_affiliations`・`/api/admin/roster/partners`）（#9301）。
  - **クライアント** = 案件をくれる会社（請求先）。**協力会社** = Field OS を使っていない会社で、スタッフを出してくれて、こちらが支払う会社。Field OS を使っている会社のスタッフは企業間連携で扱う。

### D-53 他社連携のスタッフのログインの扱いは自社だけに絞る（#9940 #9942）
今のままにしたものではなく、利用者の決定（2026-11-09「他社連携のスタッフのログインの扱いは自社だけに絞る」）で仕様を変えたものです（総点検の authz-01・authz-03）。
- **決定**:
  - 稼働先の管理者が、他社から連携したスタッフ（`linked_external` の行）のログイン中の端末を開いたとき・ログインを終了させたときは、本人がその会社に切り替えているログイン（`sessions.company_id` が自社）だけを返す・消す。所属元の会社でのログイン（接続元・端末・時刻）は見せず、終了もしない。「ログインを終了させるスタッフ」の台数も自社に切り替えている分だけ。自社雇用の行から開いたときは今までどおり、企業を切り替えた他社の画面のログインも含める（以前の docs/api.md の「同じ人の他社の行のセッションも消す」はこの場合だけになった）。
  - 連携が終わった連携行（所属元が連携を終了した `link_revoked_at`、稼働先が取引終了にした `link_ended_at`）は、スタッフアプリの企業切替の一覧・切替先・勤怠の振り分け（`personStaffRows`）と、稼働先のお知らせの今の対象（既読数の分母・メールの宛先・個人あての候補）から外す。終わった会社に切り替えたままのセッションは、次の API の呼び出しで 401（`code: 'link_ended'`）にして消し、スタッフアプリは理由を出してログイン画面に移る。ログインし直すと所属元の会社に入る。
  - 稼働先が取引状況を「稼働中・休止中」に戻すと、また切り替えられる（所属元が連携を再開しただけでは、取引終了のままなので切り替えられない）。
- **理由**: 所属元での利用の記録（接続元・端末）は他社に渡す情報ではない（D-03 の共有範囲に入っていない）。他社の操作で所属元のログインが切れるのも困る。連携を終えた相手の会社のお知らせ・シフトを本人が使い続けられるのは、連携の終了の意味に合わない。
- **影響**: 過去の勤怠・精算の記録は消さず、稼働先の画面に残る（DB の変更なし）。スタッフ本人のアプリからは、終わった会社の過去の実績・シフト・日報は見えなくなる（`personStaffRows` を使う画面）。パスワードの再設定（メールのリンク）と統合では、同じ人の全セッション（企業を切り替えた分も）を消す（#9941。`src/lib/login-security.ts` の `revokePersonSessions`）。
- **根拠のコード**: `src/lib/login-security.ts`（`personSessions`・`revokePersonSessions` の会社の絞り込み）、`src/api.ts` の `staffLoginUser`・`/admin/staff/:id/sessions`・`NOTICE_MEMBER_NOW_SQL`、`src/lib/auth.ts` の `loadSessionUser`（`link_ended`）、`src/roster.ts` の `personStaffRows`

### D-30 Workers の Free プランで動かす・PBKDF2 は 10,000 回
- **決定**: 本番は Cloudflare Workers の Free プラン（CPU 時間は1リクエストあたり 10ms）で動かす。パスワードのハッシュ（PBKDF2）は、作るときは 10,000 回にする。照合は 100,000 回まで受け付ける（Paid プランに移って回数を上げても、古いハッシュで照合でき、ログイン成功時に作り直す）。
- **理由**: 費用を抑えるため。100,000 回では Free プランの CPU 時間に収まらない。
- **影響**: 重い処理は D1 の SQL に寄せる、Web Push は本文を暗号化しない、など（[architecture.md](architecture.md) の 13 章）。
- **根拠のコード**: `src/lib/auth.ts:11`〜`14`

### D-50 打刻は最初に押した時刻で記録する（#9939。D-07 を変更）
- **決定**: スタッフアプリの打刻は、最初にボタンを押した時刻（端末の時計）を記録の時刻にする。混雑や電波で送り直しても、押した時刻のまま。ただし、端末の時計がサーバーと5分以上ずれているとき（送るたびに端末の今の時刻も送って比べる）・押してから受け付けるまでが30分を超えたとき・押した時刻がサーバーの時刻より後（未来）のときは、サーバーが受け付けた時刻で記録する。押した時刻と受け付けた時刻が1分以上違う打刻には「再送」の印（`attendance_reports.time_source` が `device` = 押した時刻で記録、`resent` = 受け付けた時刻で記録）を付け、管理者の画面（打刻の一覧・打刻修正の承認・シフトの報告状況・ダッシュボード）に小さく出す。
- **理由**: 同時80〜100人の打刻で D1 の過負荷が起き、一時的に打刻が失敗した（Sprint 19 の性能試験）。画面が自動で送り直すので、記録の時刻は押した時刻にしたい。端末の時刻は本人が変えられるので、使う範囲を30分に狭め（D-07 の12時間から変更）、違いは「再送」の印で見分けられるようにした。
- **根拠のコード**: `src/attendance-punch.ts`（punchTime）・`public/static/staff.js`（打刻の送信）
