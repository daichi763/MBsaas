# Field OS — 通信人材会社向け 運営標準化SaaS（動作モックアップ v0.1）

## プロジェクト概要
- **名称**: Field OS（ディセクテラ株式会社 想定サービスのモックアップ）
- **目的**: 通信系人材会社（携帯ショップ・家電量販店・催事・光回線などへの派遣/請負）の日次運営を標準化するSaaS。勤怠・日報・実績・シフト・フォロー・請求前チェックまでを1つに統合。
- **フェーズ**: Phase 1 動作モックアップ（仕様書 §25 準拠）。サンプルデータ入りで全画面が動作します。

## 実装済み機能

### スタッフ画面（モバイルファースト `/staff`）
- ホーム: 本日のシフト・勤怠報告状況・未読お知らせ・相談返信通知
- 勤怠報告: 起床 → 出発 → 入店（位置情報取得・写真必須）→ 退店（写真必須） の順序制フロー、遅刻自動判定
  - 入店/退店報告は写真1枚が必須。カメラ起動 / アルバム選択に対応し、ブラウザ側で JPEG・画質70%・長辺1600px・500KB以下に圧縮（Exif自動除去）してから Cloudflare R2 へアップロード
- 日報入力: 案件ごとのテンプレートから動的フォーム生成（MNP/PI/新規/機種変/光 等の数値 + 所感）、トラブル/クレームフラグ
- シフト確認・希望提出、お知らせ（既読管理・重要マーク）、自分の実績（月次集計+日別）、相談窓口（カテゴリ・緊急度・返信履歴）

### 管理画面（PC向け `/admin`）
- ダッシュボード: 本日の稼働/売上見込みKPI、未報告アラート（起床/入店/日報）、**ルールベース管理者ToDo**（日報未提出3日以上・遅刻頻発・欠勤頻発・トラブル連続・未対応相談）、直近トラブル、要フォロー一覧、案件別実績、本日シフト（欠勤処理）
- スタッフ: 一覧（フォロー/離職リスク/未報告/低評価フィルタ）、詳細（評価レーダーチャート・月次実績・フォロー履歴・日報/勤怠履歴）、**スキルシート自動生成**（印刷対応）
- 案件・クライアント管理（CRUD）、シフト管理（週間グリッド・確定/欠勤/代打）
- 日報管理（確認チェック・コメント返信）、実績分析（日別積上げグラフ・スタッフランキング・案件/クライアント別）
- お知らせ配信（全体/案件別・既読状況確認）、フォローログ、相談対応、**請求前チェック**（案件別集計・スタッフ別明細・CSV出力）

### SaaS運営本部画面（`/hq`）
- 導入企業一覧（MRR・アクティブ率・日報数・成熟度）、企業詳細（プラン/状態/成熟度/支援メモ編集）
- 日報テンプレート配布（携帯ショップ/家電量販店/催事/光回線 標準テンプレ）、伴走支援管理

## データアーキテクチャ
- **ストレージ**: Cloudflare D1（SQLite、ローカルは `--local` モード）+ Cloudflare R2（入店/退店報告の写真、非公開バケット）
- **テーブル（15）**: companies / users / sessions / staff_profiles / clients / report_templates / projects / shifts / attendance_reports / daily_reports / evaluations / follow_logs / notices / notice_reads / consultations
  - `attendance_reports.photo_key`: R2オブジェクトキー（画像バイナリ自体はDBに保存しない。マイグレーション `0002_add_attendance_photo.sql`）
- **マルチテナント**: 全テーブルに `company_id`、ログインは 会社コード+ユーザーコード+パスワード
- **認証**: SHA-256 ハッシュ + httpOnly Cookie セッション（30日）、ロール別ミドルウェア（/api/admin/*, /api/hq/*）
- **日報**: テンプレート定義（fields_json）→ 回答は JSON 保存 → `json_extract` で集計

## 入店/退店報告 写真添付機能 セットアップ

### 1. R2バケット作成（初回のみ・要手動実行）
```bash
npx wrangler r2 bucket create saasdev-attendance-photos
```
- バケットは**非公開**のまま作成してください（`--jurisdiction` 等の公開設定は行わない）。画像は必ず `/api/staff/attendance-photo/*` のログイン認証付きエンドポイント経由でのみ配信されます。
- ローカル開発（`npm run dev` / `wrangler dev`）では miniflare が R2 をローカルエミュレートするため、追加設定なしで動作します。

### 2. wrangler.jsonc（設定済み）
```jsonc
"r2_buckets": [
  { "binding": "PHOTOS", "bucket_name": "saasdev-attendance-photos" }
]
```

### 3. マイグレーション適用
```bash
npx wrangler d1 migrations apply webapp-production --local   # ローカル
npx wrangler d1 migrations apply webapp-production           # 本番
```

### 4. 型定義の再生成（R2バインディングを追加したため）
```bash
npm run cf-typegen
```

## スタッフマスタ / 従業員管理 分離・企業間スタッフ連携（フェーズA〜C）
仕様: `docs/spec_multi_company_staff.md`

- **管理画面の分離**: 「スタッフマスタ」（企業間で共有し得る情報）と「従業員管理」（旧 社員名簿。雇用・給与・口座等、自社のみ）
- **所属区分（affiliation_type）**: `own_employee`（自社雇用）/ `linked_external`（他社連携）/ `partner_manual`（取引先所属）/ `skillsheet_only`（スキルシートのみ）
- **新規作成の4つのルート**（スタッフマスタの「新規追加」ボタン）
  1. QRコード / スタッフIDから連携: 他社の自社雇用スタッフを、恒久固定のスタッフID（`persons.global_staff_code`, 例 `FS1A2B3C4D5E`）で連携。連携のたびに同意確認ポップアップを表示し、同意は `roster_consents` に記録する
  2. 従業員管理から作成: ログインアカウント・スタッフマスタ・従業員管理を同時に作成
  3. 取引先から作成: 取引先マスタ（`staff_affiliations`）から選択するか新規登録。ログインの発行は任意
  4. スキルシートのみ作成: ログインなし。既存のスキルシート生成機能をそのまま利用
- **権限制御**: 他社連携スタッフの基本項目（氏名・スキル等）は所属元企業の値を参照するだけで、稼働先はAPIレベルで編集不可（403）。メモ・評価・フォロー等の追記項目は企業ごとに独立して保持する。従業員管理は `own_employee` かつ所属元が自社のスタッフに限り参照・更新できる
- **ログインを持たない人物**: `users.role = 'roster_only'`（ログイン不可。お知らせ対象・スタッフ数集計の対象外）。既存のシフト・勤怠・評価等は従来どおり `staff_id` で紐付ける
- **API**（`src/roster.ts`。`/api/admin/*` の管理者ロールでのみ利用可）
  - `GET /api/admin/roster/consent-terms` / `GET /api/admin/roster/lookup?code=` / `POST /api/admin/roster/link`
  - `POST /api/admin/roster`（`route`: `employee` / `partner` / `skillsheet`）
  - `GET /api/admin/roster/partners` / `GET /api/admin/roster/consents[?staff_id=]`
- **マイグレーション**: `0012_add_persons_and_staff_master.sql`（`persons` と `roster_consents` を追加し、`staff_profiles` / `users` / `staff_affiliations` に列を追加。既存の `staff_id` の値は変更しない）
- **フェーズD 必須項目の企業別設定**: スタッフマスタ画面の「必須項目の設定」から変更します（変更できるのは会社管理者のみ）。氏名・性別は常に必須で変更できません。設定は `roster_field_requirements` に保存され、新規作成と基本項目の更新の両方に適用されます。①連携で登録したスタッフには適用しません。④スキルシートのみでは、最寄駅などの稼働系の項目は必須判定の対象外です
- **フェーズE QRコード**: 自社雇用スタッフのスタッフ詳細と、スタッフ本人の画面（その他 → マイプロフィール）に、恒久固定のQRコードを表示します。①連携ではカメラでQRを読み取れます。読み取りはブラウザ内の jsQR で行い、画像はサーバーへ送信しません
- **フェーズF 追記項目の共有**: 稼働先の「稼働先追記項目」（現場評価・稼働メモ。列は `site_evaluation` / `work_memo`）は、所属元のスタッフ詳細「連携先企業」パネルに閲覧専用で表示されます。各社の管理者メモ・フォロー履歴・日報は他社に公開しません
  - API: `GET/PUT /api/admin/roster/field-settings`, `GET /api/admin/roster/:id/share-code`, `GET /api/admin/roster/:id/links`, `GET /api/staff/me/profile`（本人向け。基本項目と連携用IDのみを返します）
- **フェーズG 企業間チャット**: スタッフ詳細の「企業間チャット」欄、一覧画面（`#roster-chat`）、ダッシュボードの新着通知、サイドバーの未読バッジで構成します
  - スレッドは「所属元 × 稼働先 × スタッフ」の組ごとに1本（キーは稼働先側の連携行 `staff_id`）で、参加できるのはその2社の管理系ロールのみです
  - **スタッフ本人は閲覧も投稿もできません**。APIは `/api/admin/roster-chat/*` だけに置いています（`role=staff` は 403）。`/staff` 画面は `roster-chat.js` を読み込みません。チャット欄には「このやり取りはスタッフ本人には表示されません」と表示します
  - 既読は企業単位で管理します（`roster_comment_reads`）。履歴は削除しません（`migrations/0014`）
- **フェーズH 統合ログイン・勤怠の自動振り分け**
  - ログインするのは所属元のアカウント1つだけです。同じ人物（`person_id`）が複数の企業に登録されている場合、スタッフ画面のヘッダーに企業の切替が表示されます（`POST /api/staff/me/switch-company` でセッションの付け先を変更します）。稼働先側のユーザー行は照合できないパスワードを持つため、稼働先の会社コードで直接ログインすることはできません
  - 勤怠報告・写真付き報告・日報は、どの企業を表示していても **シフトの所有企業**（`shifts.company_id` と、その企業のスタッフ行）に自動で記録されます。ホームとシフト画面には、全所属企業のシフトをまとめて表示します
  - `migrations/0015`: 連携スタッフのうち、所属元でログインを持つ人の稼働先ユーザー行を `role='staff'` に変更します
- **スタッフマスタの編集ルール（基本情報）**
  - `own_employee`（自社雇用）: 従業員管理のデータをそのまま表示します（連絡先・社員番号・所属も表示）。基本情報は **従業員管理の「スタッフ基本情報」欄でのみ編集** できます（`PUT /api/admin/employees/:id` の `profile` で送信）。スタッフマスタ側からの更新は 403 になります
  - `linked_external`（他社連携）: 閲覧のみです（所属元が管理）
  - `partner_manual`（取引先所属・システム連携なし）/ `skillsheet_only`（スキルシートのみ）: スタッフマスタ画面で編集できます（API の `can_edit_in_master` が true）
  - 管理者メモ・要フォロー・稼働先追記項目は、**全スタッフで記入** できます
- **スタッフ詳細のレイアウト**: 左の約2/3が基本情報です。右上は「ファイル」（旧 履歴書。アップロード可）、その下に評価グラフを置きます。月次実績・フォロー・日報・連携パネルは下段に並べます
- **今後の課題**: 稼働先からのお知らせメールの宛先（連携行にはメールアドレスをコピーしていない）、スタッフ本人の実績・相談画面での複数企業の横断表示

## 常勤・スポット案件のシフトボード / 単価（請求・支払）（第1段階）
仕様: `docs/spec_spot_shift.md`（第2〜5段階の計画を含む）

- **案件区分**: 常勤 / スポット（案件詳細の「区分・標準単価」で設定）
- **開催場所**: クライアント詳細の「開催場所」で登録します（今後の現場マスタの土台。`sites`）
- **募集枠**: 日付・時間・開催場所と、役割ごとの必要人数を持ちます（`shift_slots` / `shift_slot_roles`）。複数の日付にまとめて作成できます
- **繰り返し登録**: 曜日 × 期間で枠をまとめて作成します（`slot_patterns`）。作成後は日ごとに変更・削除できます
- **シフトボード**（`#shifts`。従来の週表示は `#shifts/week`）
  - 複数のクライアント・案件・開催場所を並べて表示できます（1週 / 2週 / 1か月）。「枠ごと」と「人ごと」の2つの表示があります
  - 充足（確定/必要）を表示し、不足している枠は赤くします
  - 右側のスタッフ一覧から枠へドラッグして割り当てます。枠から枠へのドラッグで移動します（移動先の単価で再計算します）
  - 枠の「＋」から候補を表示します（空き・この場所の経験・この案件の経験・スキル・今週の稼働日数・NG）
  - 同じ時間帯のシフトの重複（他社の分も同一人物として確認）と、NGスタッフを警告します
  - 表示中の範囲の請求合計・支払合計・粗利・粗利率を表示します
  - 常勤の一括登録（スタッフ × 曜日 × 期間）と、期間のコピー（枠・割り当て）ができます
- **単価（請求と支払を分けて持つ）**
  - 案件の標準単価（請求・支払・交通費ルール・休憩）と、単価ルール（開催場所 / 役割 / スタッフ別。`rate_rules`）があります
  - 優先順位: シフトの手動変更 ＞ 枠の役割の単価 ＞ 単価ルール（スタッフ ＞ 役割 ＞ 開催場所）＞ 案件の標準
  - 単位は日額（1稼働）または時給（拘束時間 − 休憩）です
  - 交通費の請求は「実費 / 定額 / 単価に込み」、支払は「実費 / 上限あり / 定額 / なし」から選びます。`shifts.transportation_fee` はこれまでどおり実費の記録です
  - 割り当てた時点の金額をシフトに記録します（`bill_*` / `pay_*` / `payee_type` など）。単価表を変えても登録済みのシフトは変わりません。変更を反映するときは「今後のシフトに単価ルールを再適用」を使います（手動で変更したシフトは対象外です）
  - `shifts.unit_price` は請求の基本額です。これまでの売上概算・請求前確認はこの列をそのまま使います
- **金額の公開範囲**: 管理画面（`/api/admin/*`）でのみ返します。スタッフ画面のAPI（`/api/staff/home`・`/api/staff/shifts`）は金額の列を取り除いて返します
- **API**（`src/shift-board.ts`）: `/api/admin/shift-board`, `/shift-board/candidates`, `/shift-slots`, `/shift-slots/roles/:id/assign`, `/shifts/:id/move`, `/shifts/:id/price`, `/shifts/reprice`, `/shifts/bulk`, `/shifts/copy-week`, `/slot-patterns`, `/sites`, `/rate-rules`, `/rate-rules/resolve`, `/projects/:id/pricing`
- **マイグレーション**: `0016_add_spot_shift_board.sql`（列とテーブルの追加のみ。既存のシフトは「枠なし」「請求 = 既存の単価」のまま動きます）
- **次の段階**: 区分の新設（日雇い・個人事業主）と区分変更の手順、仮登録、勤怠・日報の提出設定、報告用URL（第2段階）→ 実働時間の反映と請求・支払の集計・CSV出力（第3段階）→ 募集ページ（第4段階）→ 仮登録スタッフと連携スタッフの統合（第5段階）

## 区分の新設・区分変更・仮登録・提出設定・報告URL（第2段階）
仕様: `docs/spec_spot_shift.md` 6〜8章

- **区分の新設**: 自社日雇い（`daily_worker`。従業員データ不要）・個人事業主（`freelance`）。どちらもスタッフマスタで編集できます
- **仮登録**: 氏名・電話番号だけで登録し、すぐシフトに割り当てられます（電話番号の重複を確認）。後から本登録（ログイン発行は任意）
- **区分変更**: スタッフ詳細の「区分・登録状態」から。確認画面で影響を示し、適用日以降の予定シフトの単価・支払先を置き換えます。履歴を残します
  - 自社雇用から外れると従業員データは「雇用終了」として閲覧のみで保持します（退職とは別）
- **勤怠・日報の提出設定**: 案件 → スタッフ → シフトの順に上書きできます（勤怠: なし / 入店・退店のみ / すべて、日報: なし / 必須）
- **報告URL**: シフト詳細で発行してコピーし、送ります（ログイン不要、勤務日の翌日まで有効、取り消し可能、金額は表示しません）
- **代理入力**: 管理者がシフト詳細から入店・退店などを代わりに記録できます
- **マイグレーション**: `0017_add_staff_lifecycle_and_report_settings.sql`（列とテーブルの追加のみ）

## 精算: 実績の確定・請求/支払の集計・CSV（第3段階）
仕様: `docs/spec_spot_shift.md` 9章

- **精算画面**（`#settlement`）: 期間・クライアント・案件・支払区分で絞り込み、シフト明細 / 請求（クライアント・案件別）/ 支払（支払先・スタッフ別）を表示
- **実働時間**: 入店・退店報告から自動で反映（手入力も可）。時給は案件の設定（予定の範囲内 / 実績どおり / 予定どおり、丸め）で計算
- **確認事項**: 報告なし・実績未入力・予定との差・単価未設定などを表示
- **確定**: 確定したシフトは時間・金額・スタッフを変更できません（取り消し可）
- **CSV**: シフト明細・請求集計・支払集計（給与ソフトへの取り込み用）
- **マイグレーション**: `0018_add_settlement.sql`（列の追加のみ）

## 募集ページ・応募・承認（第4段階）
仕様: `docs/spec_spot_shift.md` 10章

- **募集ページ**（管理画面「募集・応募」）: 案件と期間を選ぶと、シフトボードの募集枠を公開URL・QRで募集できます（`/apply/:token`）。案件名・クライアント名・金額は表示しません
- **応募**: 日時を複数選んで、氏名・電話番号で応募します（ログイン不要）。送信回数の制限・ボット対策あり（Turnstile は `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY` を設定すると有効）
- **承認**: 日時ごとに承認・見送り。承認でシフトを確定し、未登録の人は仮登録を自動作成（電話番号が一致するスタッフへの紐づけも可）。定員超過・重複・NGを警告
- **スタッフアプリ**: 「シフト」→「募集中のお仕事」から登録済みスタッフが応募・取り下げできます
- **保存期間**: スタッフに紐づかない応募は180日で自動削除
- **マイグレーション**: `0019_add_recruitment.sql`（テーブルの追加のみ）

## 仮登録スタッフと既存スタッフの統合（第5段階）
仕様: `docs/spec_spot_shift.md` 11章

- 仮登録のスタッフ詳細 →「区分・登録状態」→「既存のスタッフに統合」。電話番号・氏名・フリガナが一致する候補（他社連携スタッフを含む）から選びます
- シフト・勤怠・日報・評価・フォロー・相談・書類・単価ルール・応募・NG指定を統合先へ移します。今日以降の予定シフトは統合先の区分で単価・支払先を置き換え、過去・確定済みの金額は変えません
- 統合元は「統合済み」として残し（削除しない）、一覧・候補・検索から外します。統合は元に戻せません
- **マイグレーション**: `0020_add_staff_merge.sql`（列・テーブルの追加のみ）

## スタッフマスタの業務側項目（経歴テーブル・PRポイント・備考）
- 考え方: **社員名簿（従業員管理）= 労務側**、**スタッフマスタ = 業務側** の情報を持つ
- 業務側項目 = 通勤可能時間・稼働開始可能日・稼働可能エリア・スキル・経歴・「経験・スキル・人柄・PRポイント等」・備考
  - **他社連携（linked_external）以外の全区分（自社雇用を含む）でスタッフマスタ画面から編集**（従業員管理画面では参照表示のみ）
  - 他社連携は所属元の値を閲覧のみ。PRポイント・備考も連携先に共有する（その会社独自の情報は管理者メモに記入。同意文面は v2 に更新）
- スタッフ詳細は **閲覧モードで開き、「編集」→「保存」（または「キャンセル」）で切り替える**。編集時は区分に応じた項目だけが入力欄になる
  - 取引先所属・スキルシートのみ・日雇い・個人事業主: 基本情報・在籍状況・業務側項目・管理者メモ
  - 自社雇用: 業務側項目・管理者メモ（労務側は従業員管理から） / 他社連携: 管理者メモのみ / 統合済み: 編集不可
- 経歴はテーブル（開始・終了・勤務・業務内容、行は任意に追加/削除、最大50行）。開始・終了はカレンダー（年月選択, flatpickr monthSelect）から選ぶ
  - 備考列は廃止し業務内容欄を拡大。以前の備考は編集時に業務内容の末尾へ引き継ぐ
  - `staff_profiles.career_rows`（JSON）に保存し、`career` には要約テキストを自動生成（一覧・連携先・必須判定・旧画面向け）
  - 旧テキスト形式の経歴は編集時に1行目の業務内容へ引き継いで表示
- 管理者メモ・PRポイント・備考などのフリー記述欄はカード全幅で表示。スキルシートにも経歴テーブル・PRポイントを反映
- マイグレーション: `0021_add_staff_business_fields.sql`（career_rows / pr_points / remarks）
- API: `PUT /api/admin/staff/:id` が `career_rows`・`pr_points`・`remarks` を受け付ける（自社雇用は業務側項目のみ可、他社連携は403）

## スタッフマスタの多段連携（2次・3次・4次受け）
- 他社から連携で受け入れたスタッフも、「連携用QR」から自社専用の連携コード（`RL…`）を発行して、さらに次の企業へ連携できる
  - 自社雇用は本人の恒久ID（`FS…`）。連携行は恒久IDを渡さない（次の企業が雇用元と直接つながらないように）
- **各社から見えるのは直接連携した前後の企業のみ**（例 A→B→C: Cの所属元は「B」、Aの連携先一覧は「B」のみ）
  - 所属会社名・所属先担当者名は自社の行の値（直前の企業）を表示。氏名・スキル・経歴などの基本項目は雇用元の最新内容を参照
  - 企業間チャットは直接連携した2社間のみ（中間企業は所属元・連携先の両方とチャット可）
  - 精算の支払先は直前の企業
- 経路は `staff_profiles.root_staff_id`（雇用元の行）として保持するが、画面・APIには出さない
- マイグレーション: `0022_add_roster_multi_level_link.sql`（root_staff_id / relink_code。既存の連携は1段目として移行）
